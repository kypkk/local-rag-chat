The honest starting point

I knew the pieces — an embedding model, a retrieval step, a vector store.

But I had never actually built one. So I didn't know the real troubles that only show up in implementation:

  • streaming tokens to the frontend
  • fitting everything into a 6K budget
  • a small model that over-refuses

RAG is two pipelines

My project: 3 layers, everything swappable

api · thin

A route only: parse request → call service → stream. Zero business logic.

service · orchestration

RagService wires the components in the right order. The "heart."

components · behind interfaces

Chunker, Embedder, VectorStore, LLMClient — each does one thing.

Why this shape

  • Three Protocol interfaces → I test the whole pipeline with fakes, no Ollama.
  • Swap NumPy store → LanceDB, or swap the model — orchestration doesn't move.
  • Built bottom-up: deterministic plumbing first (unit-tested), model last.

Backend: FastAPI · NumPy · langchain-text-splitters  ·  Frontend: pure HTML / CSS / JavaScript (no framework)

Bottom layer · the plumbing

Ingestion: docs → chunks → vectors

load_documents(.md/.txt)
      ↓
chunk_documents()
  MarkdownHeaderTextSplitter  ← headers → citation
  RecursiveCharacterTextSplitter ← split if oversized
      ↓
embed_documents()  → 768-d vectors
      ↓
store.add() + save()

The chunker is the interesting part

  • Split on markdown headers first → each chunk carries its header path as a citation breadcrumb.
  • Oversized sections → recursive split, measured in tokens (not chars).
  • 🔑 Embed the breadcrumb + body, inject only the body. A chunk whose body never names its own topic is still findable.
Model layer · plugging in Ollama

Two Ollama endpoints, two models

/api/embed · nomic-embed-text

  • 768-dim, then L2-normalized so dot product = cosine.
  • Asymmetric prefixes: search_document: vs search_query:.
  • ⚠️ Forgetting a prefix doesn't error — it silently tanks retrieval. So I encapsulate it in the embedder.

/api/chat · llama3.2:3b

  • Instruct, Q4_K_M quant — runs on Metal, ~2.5 GB.
  • Streaming: newline-delimited JSON, one content delta per line.
  • The final object carries prompt_eval_count → I verify my token estimate against it.

Both hidden behind Embedder / LLMClient Protocols — the rest of the app never imports httpx.

Orchestration layer

answer(): the conductor

trim_history         → fit 6K
condense_question    → standalone
retrieve             → hits
build_messages       → messages, kept
build_options        → num_ctx/keep
  yield {sources}    ← metadata
for token in chat_stream:
  yield {token}      ← streamed

Two things reviewers probe

  • 🔑 Asymmetry: the rewritten question goes to retrieval; the original goes to generation. Find with one, answer with the other.
  • Chunks are the residual: subtract system + history + question + reserved output from 6K, pack chunks into what's left. Guard with raise, not assert.
  • It's a generator → streaming + lazy; nothing runs until consumed.
Frontend · data streaming

One token, Ollama → the bubble

StreamingResponse(sse())
  data: {json}\n\n     ← SSE frame

fetch(POST).body.getReader()
buffer += decode(chunk)
buffer.split("\n\n")
buffer = events.pop()  ← keep tail
switch(msg.type):
  token  → bubble += text
  sources→ n → breadcrumb

The pieces that bit me

  • fetch, not EventSource — SSE-over-POST needs a body.
  • Network chunks don't align to SSE events → buffer / split / pop to reframe.
  • json.dumps is a newline guard: escapes \n inside a token so it can't fake an event boundary.
  • Model emits [1]; client resolves it to a full source footnote — citations never enter history.

What I didn't expect

The small model over-refused

A prohibition-heavy prompt made it say “I don't know” even with the answer present. Fix: lead with the positive instruction.

Streaming isn't just “print tokens”

Reframing arbitrary byte chunks into whole SSE events — the buffer/pop dance.

Token estimate ≠ reality

No local tokenizer endpoint → estimate with chars/token, then reconcile against prompt_eval_count (I run ~6% over, the safe side).
